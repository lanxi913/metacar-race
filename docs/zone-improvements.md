# 功能区合规检测——后续改进建议（给接手的人看）

当前状态：`tools/vla_zone_read.py` 的 **r10 配置**拿到过 **正确率 1000 / 总分 950**，
这是仓库里提交的版本。本文不实现任何改动，只记录已经验证过的瓶颈、试过的路子和判断，
让下一个人少走弯路。

先读 `docs/zone-mission.md`（任务口径、评分公式、读号链路、记分表）。

## 1. 分数是怎么被卡在 950 的

```
正确率 1000 → 总分 950        （−50 是加速度控制的固定成本）
正确率 928.6 → 总分 878.6     （RU1 少 1 辆蓝车：2×3/(4+3)=0.857）
正确率 500  → 总分 450        （RU2 漏报：三轮车没读到）
正确率 543  → 总分 493        （兜底「六号全报」，比少报更差）
```

- **−50 基本拿不回来**，三条实证：起步 1.1 s `|a|=7.3`（当时指令只有 `thr=0.027`，是平台
  自己的瞬态）；`thr=0.030 + steer=+0.92` 时 5.5；纯滑行 `thr=0.000` 时仍频繁 5~9（仿真抖动）。
  这条扣分**封顶且不累计**（用户确认：多次触发也只扣一次），所以只有正确率值得优化。
- 正确率的杠杆只有两个：**RU1 少 1 辆蓝车 −71**、**RU2 漏报 −500**。R02 的权重是 R01 的 7 倍。

## 2. 已经验证有效的方向（建议按这个顺序做）

### 2.1 提帧率 + 两圈兜底（r14 已验证「时间够」，但帧预算要修）

引擎是 30 fps，我们之前只按 0.25 s（4 Hz）取帧，**每辆车只剩 1~2 帧**，这是漏读的主因。

- 实测：`--shot-every 0.09`（11 Hz）+ 两圈（282.7 m）+ `V_CRUISE=4.3`，**巡航 66 s 跑完两圈**，
  73.8 s 进入读帧阶段，`--seconds 124` 下时间完全够。
- r14 失败的原因不是时间，是**帧预算被入口那块规则说明牌抢走**：车头相机的黄块闸门
  `has_yellow_blob()` 只看颜色面积，牌子吊在杆上也会命中，30 帧预算里前 4 帧全是牌子，
  Phase B 按先进先出先读它们，每帧 0.3~1.3 s，等轮到侧门帧时已接近硬上限。
- **修法（已验证离线，未实跑）**：

```python
def car_yellow_blob(img):
    """黄绿块必须落在地平线以下才算车（入口牌子吊在杆上，落在画面中上部）。"""
    hsv = cv2.cvtColor(img, cv2.COLOR_BGR2HSV)
    mask = cv2.inRange(hsv, (25, 130, 80), (45, 255, 255))
    mask = cv2.morphologyEx(mask, cv2.MORPH_OPEN, np.ones((3, 3), np.uint8))
    h = mask.shape[0]
    mask[: int(h * 0.52), :] = 0
    n, _lab, stats, cent = cv2.connectedComponentsWithStats(mask, 8)
    for i in range(1, n):
        if 150 <= int(stats[i, cv2.CC_STAT_AREA]) <= 9000 and cent[i][1] >= h * 0.52:
            return True
    return False
```

  验证结果：r14 那 4 帧牌子 → `False`；perimeter 的三轮车帧、r14 的三轮车停靠帧 → `True`。

### 2.2 Phase B 取帧排序：先读侧门帧

编号刷在**车门侧面**，车头相机只在三轮车场景有用。现在 `store` 是先进先出，
容易被车头帧占住队首。建议取出时优先选 `cid != 0` 的帧（30 行代码，已写好未跑）：

```python
def prefer_index(store):
    for i, item in enumerate(store):
        if int(item[2]) != 0:      # item = (tag, now, cid, img)
            return i
    return 0
# 用法：ocr_frame(*store.pop(prefer_index(store)), now)
```

### 2.3 缺号推理（收益最大、风险最低的一条，还没实现）

6 辆车只对应 `C-01`~`C-06` 六个编号。如果一局里读到了 **3 辆蓝车 + 三轮车 + 红车**，
那么剩下那个没出现过的编号**必然是第 4 辆蓝车** —— 直接把 928.6 救回 1000。

- 若红车也没读到：把剩余 2 个编号都当蓝车上报 → `RU1 = 2×4/(4+5) = 0.889`，
  正确率 944，仍优于 928.6。
- 实现位置：`build_violations()` 之后，`payload` 生成之前。
- 风险：如果某一局编号不是 `C-01`~`C-06`（例如多一个号），会多报一个号 → 只损失 ~0.06。

### 2.4 三轮车（RU2，权重最高）

- 15 m 处只有 0.61，**刹停 + 小步靠近后 0.97~0.99**；目标是**凑够 2 票**（判定阈值
  `score>=0.80 且 n>=2`），r10 做到了，r14 只拿到 1 票 0.82 就放弃。
- 建议：`TRI_MAX_READ` 3→5；creep 阶段每步 1.1 s、最多 3 次，总时长硬上限 9 s 别再加。
- 另一个未试的思路：**不停车**，靠侧相机在两圈里各路过一次三轮车（它停在入口杆附近），
  用两圈 8~10 m 的侧视帧投票 —— 省下 6~12 s，但 8 m 处得分只有 0.6~0.7，风险较高。

### 2.5 兜底阈值

现在是「蓝车 <3 才六号全报」。有了 2.3 的缺号推理后，建议改成
「蓝车 ==4 且三轮车有票」才不推理，其余情况一律走推理，六号全报留作最后兜底。

## 3. 试过但不推荐

| 方向 | 结论 |
|---|---|
| 车顶黄牌 OCR 读号 | 贴脸 1.2 m 也只有 29~47 px、数字 12~16 px；Windows OCR / RapidOCR / 模板匹配全失败 |
| 模板匹配认数字 | 合成模板 NCC 最高相关 0.05，不可用 |
| 多数票定类 | r9 把蓝车判成三轮车，正确率掉到 542；必须用**最高分帧**的色相 |
| 六号全报兜底 | 实测 543，比少报更差 |
| 硬编码编号 | 编号每局重排（4 次跑次数据全部吻合），只有位置固定 |
| 弯道内环路线 | 半径太小撞到停在边缘的车（r7 两次顶停） |

## 4. 工程注意事项

1. **OCR 线程会和主循环抢 GIL**：两个 `RapidOCR` 工作线程会把主循环压到 1 Hz（r4 只读到 3 个号、
   还撞了车）。必须用「Phase A 存帧 / Phase B 串行 OCR」的两阶段结构。
2. **平台会把停太久的车挪走**：读帧阶段停 11 s 左右会出现 7.9 m 位姿跳变，跟随器要能重建。
3. **`RapidOCR` 单帧 0.3~2.3 s**（中位数 ≈0.9 s），帧预算 24 帧 ≈ 22 s，别超过 30 帧。
4. 依赖装法：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple onnxruntime rapidocr-onnxruntime`；
   `yolov8n.pt` 从 `https://huggingface.co/Ultralytics/YOLOv8/resolve/main/yolov8n.pt` 下（6.5 MB）。
5. 每次改完先跑 `--self-check`（航点数、总程、分类回归 5 帧、编号正则），不用连场景。

## 2. 问题日志

### P0 超车状态机没有元素门控（会在别的场景里毁局）

**现象**：`20261024-193727`（本意跑场景 4，误连场景 1）中，车在**垂直泊车**元素内（t=198.1–226.7，`s` 1156.8→1336.7）突然左偏 3.5 m 并保持到跑次结束。

**证据**：

| 项 | 值 |
|---|---|
| 事件 | `overtake_shift_out` @ `sim_t=214.967`，`s=1289.8`，`v=7.89`，`blk=null` |
| 触发时前方障碍 | `run.csv` t=215.3：`blk_dist=47.8`，`type=6`，`id=-570532` |
| 结果 | `lat_off` 从 215.3 s 起恒为 **3.50**，直到跑次终止 |
| `summary` | `ending=ended`，`phase=hold`，`final=(-429.976, 504.677, 211.12)` |
| 停滞段 | 0 段——车没停，是**带着 3.5 m 左偏开出了泊车路径** |

**根因**（`tools/park_cs4.py:565-579`，`Overtaker._step` 的 `CRUISE` 分支）：

```python
near = self.nearest_forward(items, 0.0)
if near is None or near["v"] >= LANE_MOVING_MS:   # LANE_MOVING_MS = 1.00
    return
if near["dist"] > OVERTAKE_PREP_M:                # OVERTAKE_PREP_M = 50.0
    return
if self.clearance(items, self.offset) < PASS_CLEAR_M:  # 60.0
    return
```

只要「本道 50 m 内有慢车 + 左道 60 m 空」就并线，**完全不看当前是哪个元素**。垂直泊车段的静止车在 47.8 m 处，刚好卡进 50 m 阈值。

**影响**：任何非超车元素只要前方 50 m 内有静止车就会左偏 3.5 m。泊车元素必毁，转弯元素会压线，窄路会撞。

**同类误触发（场景 4 内部）**：192234 的 `shift_out①` 发生在 **十字路口通行**元素内：

- `sim_t=301.533` 平台首报信号灯 `GREEN remain=4.1`（全跑次唯一一条 light 事件）；
- 前车（`id=-344300`，停在 `x=-2703.4, y=-889.0`）在 t=302.4 之前一直是 `v=0`；
- `sim_t=302.567`（**绿灯后 1.03 s**）本车判定它"静止"并开始并线；
- 但前车随后以 **≈16 m/s** 起步（t=303.4 起逐帧位置 −2690.1 → −2674.1 → −2658.1…），本车 8 m/s 追不上；
- 结果：**在路口中间白白横移 3.5 m、4.4 s 后又并回来**，`lat_off` 302.9→307.3 s 峰值 3.50。

即：状态机把"刚起步的车"判成"静止障碍"，且没有"确认静止"环节。

#### P1-c 三条根因

1. **硬刹是旁路，不改控制器内部状态**（`tools/park_cs4.py:945-946`）：
   ```python
   if blk_ctrl is not None and blk_ctrl["dist"] < BLOCK_STOP_M and speed > 0.30:
       thr, brk = 0.0, 0.35
   ```
   这条只改当帧的局部变量 `thr/brk`，`speed_ctl._throttle` 内部仍停在巡航时的 **0.85**（`SpeedController(throttle_max=0.85)`，`:678` 构造）。
2. **速度一掉到 0.30 以下，硬刹条件不再成立**，上一行的残留 0.85 立刻生效 → 车往前窜 → 速度重新破 0.30 → 再次硬刹。→ **0.3 s 周期的极限环**。
3. **停定后判据自锁**：`d_eff = blk_dist - BLOCK_MARGIN_M = 4.89 - 4.80 = 0.09` → `v_cap = max(0, 0.45*(0.09-1.5)) = 0` → `v_tgt = 0` 永久保持。**没有任何退让或绕行逻辑**，只能等元素超时。

### P1e 元素名不推进（**待定性**，本轮只取数据不改）

**现象**：192234 中 `sub_scene` 从 t=316.5 一直到跑次结束（561.2 s，244.6 s）**始终是「复杂路况超车」**，即使车已经开过 `s=2312`（匝道起点）、`s=2996`（紧急停止起点）、一直开到 `s=3042.9`。平台从未切到「匝道」「紧急停止」「辅路」。

**两个假设**：

- H1：平台在连续场景里**只有元素判定通过才更新名字**；本车虽然开过了位置，但没满足完成条件，名字就钉在元素 6。
- H2：平台按**时间线**推进，元素 6 到期（200 s）后重开而不是前进，所以名字永远回到元素 6。

**旁证**：本车停定位置 `s=3042.9` **恰好等于**交接文档里「紧急停止」元素的**终点**（2996.5–3042.9），且前车 `id=-132956` 是"同向前车从 30 m 外减速停在车头前 4.89 m"——这正是紧急停止场景的标准编排。也就是说**本车的停止动作可能是对的，只是平台不认账**。

**影响判断**：这一点决定 P1 的改法完全不同——H1 要补"元素完成判据"，H2 要改"按名字推进的逻辑"。所以**本轮不猜**，只加探针（见 §3）。

**关键旁证（能低成本裁掉一半猜测）**：`metacar.models.SubSceneInfo` 除 `name` 外还带 `start_point` / `end_point`（`Vector3`）：

```python
class SubSceneInfo(BaseModel):
    name: str = Field(alias="SubSceneName", ...)
    start_point: Vector3 | None = Field(alias="StartPoint", ...)
    end_point: Vector3 | None = Field(alias="EndPoint", ...)
```

而 `static.sub_scenes` 就是全部 12 个元素的表（`:752-753` 正是按名字在里面查 index）。**把每个元素的 `start_point/end_point` 投影到路线上就能算出它的 `s` 区间**——于是可以离线对比「按位置算出来的元素」和「平台报的元素名」，H1/H2 一次跑次就能裁决，而且还能顺手校验交接文档 §元素里程表。

## 6. 本轮探针结果（跑次 `20261024-202203`，门控+探针版，14221 帧 / 474.0 s）

### 6.1 元素里程表 — 与交接文档逐字一致

开跑第一条 `elements_by_pos` 就把 12 个元素的 `s` 区间算出来了，和交接文档那张表**完全对上**（8.2~59.2 / 60.1~1083.0 / 1084.0~1582.6 / 1583.7~1661.8 / 1662.8~1985.3 / 1986.3~2312.5 / 2312.5~2995.5 / 2996.5~3042.9 / 3067.8~4404.5 / 4405.5~4422.1 / 4423.1~4644.3 / 4645.4~4718.5）。`element` 事件里的 `end_s` 与我们投影的值一字不差 → **`sub_scenes[].end_point` 可信，可以直接拿来做控制判据。**

### 6.2 【关键】元素推进的几何规律：过边界时必须贴着路线

| 边界 | 平台是否推进 | 越过该 `s` 那一帧的 `lat_err` | 边界 ±12 m 内 `|lat_err|` 最小值 |
|---|---|---|---|
| 59.2 | ✅ → 连续转弯 | **+0.00** | 0.00 |
| 1083.0 | ✅ → 环岛 | **−0.06** | 0.00 |
| 1582.6 | ✅ → 车辆跟随 | **+0.18** | 0.00 |
| 1661.8 | ✅ → 十字路口 | **+0.01** | 0.00 |
| 1985.3 | ✅ → 复杂路况超车 | **−0.00** | 0.00 |
| **2312.5** | **❌ 卡住** | **+2.83**（`lat_off` 还在 +1.22，回中没走完） | **0.35**（但要到 2324 才收敛，已过界 12 m） |
| 2995.5 | ❌（已卡） | +0.06 | 0.00 |
| 3042.9 | ❌（已卡） | +0.00 | 0.00 |

→ **5 次成功切换全部发生在 `|lat_err| ≤ 0.18 m` 的帧上；唯一失败的那一次是 2.83 m。** 而且失败之后再干净地越过 2995.5、3042.9（lat 都是 0.00）也**不补判** → 判定是**一次性**的，错过那个窄窗口就永远卡在元素 6。

**结论（P1e 定性）**：不是"元素名显示不更新"，是**平台状态真的冻在元素 6**——`used` 从 0.3 s 一路涨到 **155.6 s**，`end_s` 恒为 **2312.5**，`end_dist` 从 5.2 m **反向涨到 646.1 m**，三者同步冻结。

**由此推翻交接文档对 P1 的描述**：卡住场景 4 的根因不是"元素 6 之后被静止车顶死"，而是**超车回中太晚，越过元素终点时车还在左车道 2.83 m 处，平台判元素 6 未完成**；之后所有元素都不计分，200 s 到点被拽回。

### 6.3 元素 8「车辆紧急停止」：我们可能本来就该停车

- 车最后停在 **s=3042.9**，正好是**元素 8 的终点**；前方 4.89 m 是一辆 `ori=90°` 横停的车（`id=-132956`，`len=4.0`）。
- 也就是说"顶死"的位置恰好是"紧急停止"该停的位置。平台没进元素 8，这辆车**很可能从未被激活**（两次跑次加起来它 1684 帧 `v=0` 没动过）。
